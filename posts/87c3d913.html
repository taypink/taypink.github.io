Hexo迁移Astro分析

发表于2026-11-09|更新于2026-11-14|Lifeline
|字数总计:2.6k|阅读时长:8分钟|阅读量:

categories: Lifeline

plan time：27Y

一、 方案构造

  • Old：Hexo + Butterfly + GitHub Pages (单公开仓库) + PicGo + 阿里云 OSS
  • New：Astro 引擎 + 传统博客主题(暂定) + Shiki (Expressive Code) + 原生 Mermaid / 本地 Kroki 容器 + Pagefind + 双仓库隔离(Private 源码 -> GitHub Actions -> Public 静态 Pages) + PicGo (WebP) + Cloudflare R2 + 个人独立域名

二、 核心选型背景与迁移考量

1. 为什么放弃 WordPress、Hugo 与 Hexo，转向 Astro？

考虑到动态博客部署麻烦，日后维护也折腾，坚决选择去 JS、纯静态的方案。 * WordPress：动态博客太重，涉及数据库和动态环境维护。 * Hugo：虽然速度快，但 Go Template 模板语法很难写，用起来反直觉。 * Hexo：历史包袱太重，各种小问题积攒多年。碰巧刷到有人迁移博客，深入了解后发现 Astro 的现代化设计刚好能解决我目前所有的痛点。 * MkDocs Material: 要手写语法高亮、不能自由调节布局

2. 多层级子目录与路由设计（对齐 NetBox 资产思路）

  • 痛点：Hexo 对深层级目录支持很弱，文件夹层级一旦嵌套深了，文章分类和路由就容易出问题。
  • Astro 优势：Astro 的 Content Collections 原生支持任意深度的子文件夹，能直接按照文件夹的物理层级生成清爽的 URL（比如 /network/routing/bgp/）。这与平时做网工规划时，使用 NetBox 整理架构树和设备层级的思路完全契合。
  • 主题选择：不考虑官方的 Starlight 这类文档主题，也不考虑双栏 Wiki。我还是更习惯传统博客的阅读质感，后续会在社区挑选干净的主题作为基底，重点把侧边目录栏（TOC）和多级分类展示调通。

3. 告别本地环境折磨与强刷（双仓库隔离 + GitHub Actions）

  • 本地环境痛点：Hexo 时代简中圈教程大多只教本地部署，导致电脑里必须同时保留源码和编译出来的静态文件。不仅占空间，对 Node.js 版本要求还极其苛刻。之前我从笔记本迁移到 PC 上写博客，光是重新配置 Node.js 和打包环境就折腾了半天。
  • 刷新痛点：Hexo 本地经常遇到缓存残留，总得反复敲 hexo clean 甚至手动删 public 文件夹，浏览器还得频繁按 Ctrl+F5 强制刷新才能看到变动。
  • 仓库安全问题：如果直接把放 Markdown 原文的仓库设为公开，即便文章加了密码或者标记了草稿，别人点进 GitHub 仓库照样能直接看明文，写一些涉及真实网络拓扑或未公开笔记时很不安全。
  • Astro 解决方案：
    • 构建与缓存：Astro 底层基于 Vite 构建。静态资源文件名会自动生成内容哈希，配合入口文件的协商缓存，改了内容重新打包后，浏览器会自动精准拉取新文件，没变的内容秒读缓存，彻底告别强刷。
    • 私有源码仓（Private）：平时在本地只当纯编辑器使用，不装复杂的全局打包依赖。写完直接 Git push 推到私有的源码仓库，未完成的草稿和敏感网络配置对外界完全不可见。
    • 公开静态仓（Public）：由 GitHub Actions 在云端容器免费安装依赖并编译，随后把生成的静态 HTML 自动推送到公开的 GitHub Pages 仓库对外展示。既解决了源码隐私问题，又白嫖了免费托管。

4. 契合网工职业特性：厂商配置语法高亮

  • 痛点：日常记录很多网络设备的排错日志和配置，Hexo 和 Butterfly 自带的代码高亮对网工非常不友好，完全不支持 Cisco、Arista、华为等厂商的关键词高亮，读起来就是一整块白字，排错对照极其费劲。
  • Astro 优势：原生支持 Shiki 和 Expressive Code，它底层直接使用和 VS Code 一样的 TextMate 语法规则。我可以直接把 VS Code 里的厂商高亮模板抽出来给它用，直接还原专业级高亮，甚至还能实现终端窗口外框和行高亮对比。

5. 架构图与报文图编译：告别手动去 Kroki 复制中转

  • 痛点：网工文章极其依赖拓扑图、网络报文格式图和时序图。Hexo 自身处理不了矢量图，以前画 PlantUML、Graphviz 或者 Packet Diagram 报文图，每次都得先去 Kroki 官网手动生成 SVG，再复制出来贴进文章；文章末尾还得另外备份一份图表源码。改动拓扑时两头都要改，维护起来太累了。
  • 解决思路：
    • 写作预览：本地用 Typora/Obsidian 配合 Kroki 插件，保持秒级实时预览。
    • Mermaid 走原生：Mermaid 属于轻量 JS，直接使用 Astro 原生插件处理，不需要让 GitHub Actions 多开无头浏览器容器，减轻服务器负担，也原生适配暗色模式。
    • PlantUML / Graphviz / Packet Diagram 走本地容器：为了不给 Kroki 官方服务器添负担，在 GitHub Actions 脚本里顺手拉起一个 Kroki 基础容器，打包时直接在本地内网生成内联 SVG，配合 GitHub 的构建缓存，下次没改图就不重复请求。本地只管存一份纯文本代码，写完即走。

6. 样式解耦与暗色模式适配

  • 样式同步：Butterfly 的样式跟模板绑得太死，改起来牵一发动全身。Astro 具备组件作用域隔离，后续直接把本地 Typora/Obsidian 里看习惯的深色 CSS 提取出来，挂在正文容器上就能直接用，完全不会影响导航栏和侧边栏。本地写文章保持纯正 Markdown 语法，不折腾复杂的双链。
  • SVG 滤镜适配：平时习惯看深色模式，而 Kroki 默认吐出来的图表通常是黑线白底。后续在正文 CSS 里专门针对图表容器加上反色滤镜，精准把黑线图翻转为白线黑底，同时避开网站 Logo 和普通图标，防止误伤。

7. 全文搜索与交互精简

  • 搜索方案：文章多了之后检索是强需求。放弃 Hexo 动辄几兆、加载卡顿的 search.xml，改用基于 Rust 的 Pagefind。打包后自动生成分片索引，按需加载，原生支持中文，响应速度极快。
  • 评论区：博客只做个人技术沉淀和查阅备忘，不加任何评论区，保持页面纯净。

8. 图床与域名：彻底甩掉阿里云 OSS

  • 痛点：阿里云 OSS 境外流量贵得离谱，而且每个月快到期时的营销和催费短信实在太烦人，七牛云等国内产品也不想用。
  • 解决方式：换到 Cloudflare R2，每月 10GB 免费空间，而且完全免出站流量费。反正平时主要自己查阅，常年开着代理，以后也考虑出国，大陆晚高峰卡不卡无所谓，更不想去搞繁琐的ICP域名备案。
  • 落地细节：自己买个便宜的独立域名托管在 Cloudflare，主域名指给 GitHub Pages，子域名分给 R2。PicGo 安装 S3 插件对接 R2，配合 WebP 插件在上传时自动压缩分辨率，省空间且加载更快。以前存的本地图片，后面用脚本批量上传替换即可。

三、 待处理疑点与后续办事项（To-Do）

  1. Butterfly 主题专属标签清洗 旧文章里部分类似 note、tabs 的非标准 Markdown 语法，迁移时视数量决定是通过正则脚本一键替换为标准语法，还是装个插件做兼容。

  2. Astro 博客主题最终选型 对比主流的纯静态主题（如 Fuwari、AstroPaper 等），选一个结构干净、容易注入本地 Typora CSS，并且能方便加上侧边目录栏的主题当基底。

  3. GitHub Actions 跨仓库推送权限配置 配置从私有源码仓向公开 Pages 仓推送静态文件的 Deploy Key，确保本地 push 后，云端编译打包能自动发布到公网。

4.只维护一份 MD，AI 自动翻译、缓存并做“增量/段落级更新”

→考虑用Github Action+Github Secrets？或者别的更优替代方案

5.博客分类和tag的取舍问题？只要其中一个还是我都要？

三个还是四个分类？Network(技术)、Carrer(职场、项目、规划、考证)、Life(生活、看病、书摘、) 胡思乱想和记录呢？ 技术类文章多用tag？协议、厂商、工具、code语言、场景

6.Kroki 容器的增量缓存策略 ，是否需要这样做？ 在 GitHub Actions 里起本地 Kroki 容器时，建议编写一个简单的自定义 Remark 插件（约 40 行 TS 代码）：对 Markdown 里的 plantuml / graphviz / packetdiag 代码块内容计算 SHA-256 哈希，先去 .astro/kroki-cache/<hash>.svg 找缓存，未命中再发 HTTP 请求给 http://localhost:8000 并落盘。随后在 GitHub Actions 里用 actions/cache 缓存 .astro/kroki-cache 目录——这样即使全站有几百张拓扑图和报文图，每次新增文章构建也只需几秒钟。

7.SVG 暗色模式滤镜用“色相旋转”保真 在正文 CSS 中针对 Kroki 生成的 SVG 容器做暗黑模式适配时，不要只写 filter: invert(1);，强烈建议写成：

8.Expressive Code 与 Shiki 协同 在 Astro 中直接安装 astro-expressive-code 即可（它底层已经完整封装了 Shiki）。你只需把 VS Code 插件里的厂商语法 .json 文件放进项目目录，在 ec.config.mjs 的 shiki.langs 数组里引入，就能直接在 Markdown 里使用 cisco` 或huawei` 并获得终端边框和代码行高亮能力。

9.Material for MkDoc的 Code Annotations（代码注释气泡）——在代码行尾放一个 (1) 小加号，点击就能弹出对这行网络配置的详细解释

折腾笔记迁移与 AI 翻译”是典型的拖延伪勤奋

  • 想把笔记搬到 Astro、接入 AI 翻译，本质上是在用“搭建完美的学习工具”来逃避“痛苦的开口练习”。
  • 机器翻译出来的英文是静态文本，留在笔记里救不了你的口语；你在面试或工作中需要的是即时流利度（Spontaneous Fluency）。
